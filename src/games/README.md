# 1868 交渉エンジンと振り返り

## 状態の境界

- 通常会話は1ターンにつきGemini APIを1回呼ぶ。同じ応答で発言、意味イベント、獲得情報、新政府側の実行可能性評価を受け取る。
- JSON Schemaとクライアントの検証を通ったイベントだけを、決定的なReducerに渡す。検証失敗時は発言・台帳とも反映しない。自動再試行はせず、プレイヤーが再送できる。
- `canonicalLedger.proposals/events`が合意の正本。`issues`と画面用台帳は派生値。受信時とReducerの正規化は同じ形式を再入力してもID・依存条件を失わない。
- 旧セーブとの互換性のため `agreed` / `tentatively_agreed` と9論点のIDを維持する。`peaceful_transition`が指示書の`transition`に対応する。治安・市民保護・無血移行を同時に扱う発言は、意味イベントで該当する全論点を記録する。
- Packageのacceptは全対象論点へ適用する。条件の一部だけを確認した場合、関係のない未決提案を消さない。依存条件は確定合意を起点とする固定点計算で解決し、循環依存を確定合意としない。
- 決着と反芻はCanonical Stateのみを読み、会話の再解釈もAPI呼び出しも行わない。NOT_READYの発言は実際の未決論点に限定する。勝海舟が受諾した決着の再評価は合意を取り消さない。
- 新政府判定は勝海舟の受諾後のみ実行する。政府受諾・信頼性・整合性が低い場合も合意済み論点を未解決へ戻さない。政府承認待ちの上申と、個人による越権保証を別評価する。

## 結末と記録

- Ending → 「交渉を振り返る」 → Review → 「もう一度、三月十四日へ」。Reviewはアプリ内の画面であり、専用URLには依存しない。
- 結末確定時に会話、取得済み情報、結末本文、日時をコピーしてfreezeし、進行中セーブとは別の`completed-run`に保存する。保存失敗は画面に表示する。
- 最終決着の要求と勝海舟の返答も会話履歴へ含める。Reviewで新しい攻略情報や内部数値を開示しない。
- 再挑戦は進行中の交渉を初期化する。前回の完成記録は次の結末まで維持し、タイトルから参照できる。

## 検証

```powershell
npm.cmd run test:edo
npm.cmd run test:edo:live
npm.cmd run build
```

ライブテストは環境変数`GEMINI_API_KEY`を使用する。ブラウザ保存キーを読み取らない。`test-results/edo-1868-live-report.json`に会話・台帳・判定を保存するが、キーや認証ヘッダは保存しない。

2026-09-22〜23の検証では、協調Package、新政府承認、強硬決裂、添付会話に基づく治安引継ぎと政府承認待ち、裏付けのない過大保証の5シナリオを確認。単体テストは受信処理を通す回帰テスト、短い受諾、曖昧な対象、依存条件、明示的撤回、原子的検証、決着の再評価、新政府判定の分離、Snapshotの独立性を含む。

## 制約

- 自由文の意味抽出と実行可能性の評価にはモデルの揺らぎが残る。抽出の形式と参照先の不整合は検証で止め、過去の合意を後から自由に再判定しない。
- 旧版ですでに記録から欠落した合意は、会話を再解釈して自動復元しない。既存台帳にある合意を保持して移行する。
- モバイル検証はブラウザの320/360/390/412/430px幅とPC幅。Android実機のソフトキーボードやブラウザバーの挙動は未検証。

## Ending / Review / Replay（2026-09-23）

結末は `edo1868-ending.js` がCanonical Stateから固定したSettlementSnapshotを使って描写する。受諾済みの約束と履行済みの出来事を区別し、エンディング用の追加LLM呼び出しは行わない。

- `/games/edo-1868/ending`: 最新のCompletedRunの結末。
- `/games/edo-1868/review`: 同じ記録の結末要約、発見済みノート、時系列の会話。
- 再挑戦は進行中のゲームだけをリセットする。直前のCompletedRunは保持する。
- リロード・直接アクセスでは保存した記録を表示する。記録がない場合はタイトルへ戻る導線を表示する。
- 旧記録は保存済みの結末を維持して移行する。過去の会話から約定を推測し直さない。

`npm.cmd run test:edo` は結末Snapshotの回帰テストも実行する。画面検証は `node scripts/create-edo-ending-fixture.mjs` 実行後、Viteの `/test-results/edo-ui-fixture.html` から開始できる。合意済み再現データで、決着要求 → 政府判断 → 結末 → レビューの全履歴展開 → 再挑戦まで確認する。このローカル検証ページは本番ビルドに含まれない。

## 一発勝負の決着（2026-09-25）

- NOT_READYのみ通常交渉を継続できる。ACCEPTED後は条項変更・会話・再審査を禁止し、政府の承認／不承認から直接結末へ進む。再読み込み後も確定状態を維持する。
- 政府の条項別審査と内部根拠は保持する。結末・レビュー・保存済み記録の表示には承認結果だけを渡し、修正案は公開しない。
- 今回の検証は指示により外部LLM APIを使用せず、上記3ケースの決定的テスト、関連テストとビルドのみ実施する。

## 三段階審査と物語型結末（2026-09-30）

政府審査v3はblockingとuncertaintyを区別する。過大な義務、軍事統制回復の欠如、重大な矛盾は空手形。承認可能な和平の実施上の不確実性は薄氷の和平。実行可能で重大な問題・残る不確実性がない約定は江戸無血開城。限定的な期限付き生活支援には財源の細かな明記を必須とせず、全額扶持・全員任用の裏付け要件は維持する。

総攻撃の中止・猶予・継続は既存条項factsのassault属性で保持する。中止属性が未記載でも、和平の承認から総攻撃回避を導出する。政府拒否は約束の不存在を意味しない。結末本文は追加APIなしの物語とし、約定の原文・継承条件はレビューに表示する。旧記録の結末IDは変えず表示を更新する。

決定的テストで実行可能な和平、軽微な不確実性、過大保証を比較する。実際の自由文抽出の精度は今回の検証範囲外であり、実APIは使わない。

## 5段階の歴史的到達状態（2026-10-04）

- `bloodless`（★★★★★ 江戸無血開城）、`fragile_handover`（★★★★☆ 和平成立）、`ceasefire`（★★★☆☆ 停戦成立）、`empty_promises`（★★☆☆☆ 空手形）、`breakdown`（★☆☆☆☆ 交渉決裂）。点数や不確実性の件数で分類しない。
- `ACCEPTED`はその場で結んだ約定の確定を意味する。全体の和平に加え、独立して双方が確定受諾した戦闘停止条項があれば、残る論点を解決済みにせず `settlementScope: ceasefire` として決着可能。片側の提案・条件付き受諾・未成立の前提に依存する停止条項では終了しない。新しい交渉状態や再交渉経路は追加しない。
- 政府は確定した約定を独立に審査する。過大保証等のblockingを先に判定し、該当すれば★2。問題がない停戦で、延期または恒久的移行が未成立なら★3。恒久的な移行が合意済みで実施上の実質的な不確実性が残れば★4、実行可能なら★5。
- 単なる未言及は明示的な危険と区別する。城・武装・治安・軍艦の移行が未成立の場合は、停止合意の存在を前提に★3候補とする。朝廷裁可や行政上の未確定事項だけでは★4にしない。従来の完全な無血移行合意は、独立したassault属性がない旧形式でも維持する。明示されたpostponedはcancelledへ読み替えない。
- 軍艦の共同監督だけを唯一の解にしない。新政府による実効的な指揮・保管や、使用制限を伴う共同指揮も統制の別経路となる。各役割の属性は混同・自動コピーしない。治安の段階引継ぎ・共同警備・役割分担は既存のtransitionという意味へ構造化する。
- 過去のending ID、governmentReview、CompletedRunの条項と結果は再審査しない。保存済みIDに基づく表示名・星だけを対応させる。旧alternative_peace / unfinished / assault / scorchedは読み取り互換として残す。新規の通常フローは5種類のみ。
- 10月4日の実保存JSONから過大保証fixtureを抽出した。直近の成功プレイの生JSONは未提供であり、成功fixtureは指示書の人力報告からの再構成。以前の実保存JSONに基づく軍艦監督修正の回帰も維持する。モデル応答を新しく生成した結果とは区別する。
- 検証は外部LLM APIなし。通常の関連テスト、5段階fixture、保存互換、複数の成功経路、320/390/412px・PCでの画面確認。前回の原文保持・引用表記差・phase欠損・エラー表示の回帰を維持する。


## 初回案内・API同意・出力報告（2026-10-05）

- `EdoOnboarding.jsx` が実際のUIを対象とする7ステップ案内、フォーカス制御、報告文編集を担当する。対面画面の表示後に初回案内を開始し、完了・スキップ・Escapeを同じ完了扱いにする。設定から再表示できる。
- `byokey-lab:edo-1868:tutorial-version` と `byokey-lab:edo-1868:api-consent-version` を独立管理する。現在は各1。同意versionが一致しない場合、キーの保存と会話送信を止め、設定へ案内する。再同意が必要な更新時は `CONSENT_VERSION` を変更する。
- キーは従来の `byokey-lab:edo-1868:gemini-api-key`（localStorage、暗号化なし）に保存。UIはpassword入力のlive valueだけを設定し、HTML value属性には記録しない。通信はGoogle公式の `x-goog-api-key` ヘッダーを使い、URLへキーを含めない。ブラウザ内の実行時アクセスまで防ぐ暗号化ではない。
- 報告は既存のBYOKey Lab Google Formsへ手動で引き渡す。対象のAI出力、理由、任意コメント、生成時モデルと日時、機能versionのみを編集・コピーする。この画面からPOSTや自動送信は行わず、フォームへの貼り付けと最終送信は利用者が行う。コピー完了を報告受付成功と表示しない。既存Workerは公開URLとブラウザ向け受付設定を確認できないため変更・接続しない。
- 会話の生成時に `generatedBy: gemini`、モデル、日時を保存する。定型挨拶・決着の固定文・プレイヤー発言には報告ボタンを付けない。旧保存には生成元の証拠がないため推測で付与しない。
- 報告文には設定や会話全文を含めず、現在キーの完全一致とGeminiキー形式を除去する。個人情報は利用者が編集・確認する。Google Forms自体のデータ取扱いも適用される。
- promptFeedback.blockReason / candidate.finishReason / safetyRatings.blockedをJSON解析前に確認する。安全・禁止内容ブロックは再表現を案内し、HTTP失敗と区別する。プロバイダー生エラー本文は表示・ログ出力しない。safetySettingsは未指定の既存状態を維持し、緩和しない。
